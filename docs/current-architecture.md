# Continuum — Current Architecture Audit

Snapshot of what actually exists in the repository today (2026-08-10), read against
`ERD.md` ("Continuum — Engineering Requirements Document"). This document does not
propose changes — it records the current state and flags where it diverges from the ERD.

---

## 1. Frontend architecture

- **Stack**: TanStack Start (React 19, file-based routing via `@tanstack/react-router`),
  Vite 8, Tailwind CSS v4, shadcn/Radix UI component set under `src/components/ui/`.
- **Origin**: scaffolded/edited via Lovable (`AGENTS.md` warns against rewriting
  published git history because commits sync back to Lovable's editor).
- **Routing** (`src/routes/`):
  - `/` (`index.tsx`), `/auth`, `/signup`, `/reset-password` — public.
  - `/_authenticated/*` — layout route (`route.tsx`) that gates children behind a
    client-side `beforeLoad` check (`supabase.auth.getUser()`), redirecting to `/auth`
    if unauthenticated.
    - `/dashboard` — vendor overview; renders **hardcoded sample data** (health
      breakdown, alerts-by-type, upcoming reviews, material changes, tasks) alongside
      a live query of `vendors`. None of the alert/health widgets are backed by real
      data yet.
    - `/vendors` — live list of the `vendors` table (no filtering/search wired up
      despite UI controls being present).
    - `/vendors/new` — manual vendor form → inserts directly into `vendors` via the
      browser Supabase client.
    - `/vendors/upload` → `/vendors/review` — CSV/file "import" flow. Upload only
      reads the filename (no CSV parsing) and stages a draft in `localStorage`
      (`src/lib/vendor-options.ts`); review screen inserts the draft into `vendors`.
  - `routeTree.gen.ts` is generated by the TanStack router plugin (checked in, marked
    "do not edit").
- **State/data fetching**: `@tanstack/react-query` for server state, plain
  `useState` for forms. No global store.
- **Auth in the frontend**: all Supabase calls from routes/components use the
  browser client (`src/integrations/supabase/client.ts`) directly — there is no
  API/service layer between UI and Supabase for vendor CRUD.
- **Companies House UI**: **none**. The provider integration (`src/integrations/companies-house/`)
  exists only as a server-side library + one server function (`check.ts`) + a local
  CLI script. Nothing in `src/routes` calls it, and there is no alerts/monitoring
  screen, evidence view, or resolution UI.

## 2. Supabase setup

- **Project**: linked via `supabase/config.toml` (`project_id = vwykkpoctjnhawtmgjvq`)
  and `supabase/.temp/*` (untracked local CLI cache — should not be committed).
- **Three Supabase client entry points**, each with a distinct purpose:
  - `src/integrations/supabase/client.ts` — browser client using the public
    anon/publishable key. Auto-generated ("do not edit directly" — Lovable-managed).
  - `src/integrations/supabase/client.server.ts` — server-only client using
    `SUPABASE_SERVICE_ROLE_KEY`, **bypasses RLS**. Lazily constructed via a `Proxy`
    so importing the module doesn't throw if the env var is absent until first use.
  - `src/integrations/supabase/auth-middleware.ts` /
    `auth-attacher.ts` — TanStack Start function middleware pair: the client attacher
    puts the user's bearer token on outgoing server-function requests, and the server
    middleware (`requireSupabaseAuth`) validates it via `supabase.auth.getClaims()`
    and exposes `userId`/`claims` to the handler. Used by RLS-scoped server functions
    (not currently wired into any handler in the repo — `check.ts` does not use it).
- **No `supabase/functions/` directory** — there are no Supabase Edge Functions.
  All "backend" logic is TanStack Start **server functions** (`createServerFn`,
  e.g. `src/integrations/companies-house/check.ts`) and `.server.ts` modules that
  run inside the Node/Vinxi server process, not as separately deployed Supabase
  functions. This is a legitimate alternative to Edge Functions given the ERD's
  "Supabase-backed server-side services / Edge Functions" wording, but it means
  Companies House monitoring cannot currently be invoked by Supabase `pg_cron` /
  `pg_net` — those can only reach HTTP endpoints (Edge Functions or a public app
  route), and no such route exists yet.

## 3. Existing tables & migrations

Six migrations in `supabase/migrations/`, applied in order:

| Migration | Introduces |
|---|---|
| `20260810093908_...` | `profiles` (1:1 with `auth.users`), `update_updated_at_column()` trigger fn, `handle_new_user()` trigger on `auth.users` insert, RLS policies scoped to `auth.uid() = id`. |
| `20260810093923_...` | Revokes public/anon/authenticated EXECUTE on the two trigger functions (hardening — triggers should only run via the trigger mechanism). |
| `20260810100603_...` | **Recreates `profiles`** without the FK to `auth.users(id)` and without `ON DELETE CASCADE` (drops the earlier CASCADE — see conflicts below), adds DELETE grant, redefines `handle_new_user()` identically. This looks like a Lovable-generated corrective migration rather than a deliberate schema change. |
| `20260810102504_...` | Adds `country`, `industry`, `company_size`, `primary_currency`, `time_zone`, `phone`, `designation` to `profiles`; adds `team_invites` table (invite by email, RLS scoped to `inviter_id`); extends `handle_new_user()` to populate the new profile columns from signup metadata. |
| `20260810111100_...` | Creates `vendors` (see below). |
| `20260810120000_companies_house_monitoring.sql` | Adds `vendors.companies_house_number`; creates `vendor_company_snapshots`, `vendor_monitoring_alerts`, `vendor_monitoring_failures`. |

**Actual schema today:**

- `public.profiles` — `id` (no longer FK'd to `auth.users`), `full_name`,
  `organization_name` (free-text, not a real org/tenant), plus the onboarding
  fields added later. One row per user, populated by the `handle_new_user()` trigger
  from `auth.users.raw_user_meta_data`.
- `public.team_invites` — invite records scoped to `inviter_id` (a user), not an
  organisation. Never turns into membership — there's no code that accepts an
  invite and creates access for the invited person.
- `public.vendors` — `id`, **`owner_id`** (FK → `auth.users`, cascade delete),
  `company_name`, `country`, `category`, `internal_owner` (free text, not a user
  reference), `risk_level`, `email`, `internal_vendor_id`, `source` (default
  `'manual'`), `companies_house_number`, timestamps. RLS: all four policies use
  `auth.uid() = owner_id` — i.e. vendors belong to an individual user, not an
  organisation.
- `public.vendor_company_snapshots` — append-only, one row per Companies House
  check, `raw_response` preserved as `jsonb`. RLS: SELECT only, gated through a
  `vendors.owner_id = auth.uid()` join. No `organisation_id`.
- `public.vendor_monitoring_alerts` — one row per detected attribute change,
  `severity` (`critical|attention|info`), `status` (`open|acknowledged|resolved`),
  and a **unique `dedupe_key`** (`vendorId|source|attribute|prev|new`) enforced by
  a unique index — this directly implements the ERD's duplicate-alert-prevention
  requirement. RLS: owners can SELECT and UPDATE (acknowledge/resolve), gated the
  same way as snapshots. No `organisation_id`, no `change_event` table separate
  from the alert, no resolution metadata (no `resolved_by`, `resolution_type`,
  `resolution_reason`, `resolved_at`).
- `public.vendor_monitoring_failures` — one row per failed Companies House call
  (`error_type`, `http_status`, `message`). RLS: SELECT only.
- **No `organisations`, `organisation_members`, `vendor_identifiers`,
  `trust_profile_attributes`, `external_snapshots` (generic/multi-provider),
  `monitoring_runs`, `change_events`, `audit_events`, or `vendor_monitoring_config`
  tables exist.** The two migrations that do exist for monitoring
  (`vendor_company_snapshots`, `vendor_monitoring_alerts`, `vendor_monitoring_failures`)
  are Companies-House-specific tables, not the provider-agnostic tables the ERD
  specifies (§8–§14).
- All tables have RLS **enabled**; grants are split between `authenticated` (scoped
  by policy) and `service_role` (full access, used only by the server-role client).

## 4. Authentication

- Supabase Auth (email + password), via `supabase.auth.signUp` /
  `signInWithPassword` / `resetPasswordForEmail` in `src/routes/signup.tsx` and
  `src/routes/auth.tsx`.
- Sign-up captures organisation/profile fields as **`auth.users.raw_user_meta_data`**
  (not written directly by the client to `profiles`); a `SECURITY DEFINER` trigger
  (`handle_new_user`) copies that metadata into `public.profiles` on insert.
- Session persistence: browser client uses `localStorage`, `persistSession: true`,
  `autoRefreshToken: true`.
- Route protection is **client-side only**: `_authenticated/route.tsx`'s
  `beforeLoad` calls `supabase.auth.getUser()` and redirects unauthenticated
  visitors. All authenticated routes are also marked `ssr: false`, so there's no
  server-side gate on the initial HTML for those pages — protection relies entirely
  on RLS at the data layer plus the client-side redirect (which is the correct
  belt-and-braces model for Supabase apps, but worth naming as "no SSR auth check").
- Server functions that need an authenticated user use the
  `requireSupabaseAuth` middleware, which validates the bearer token via
  `supabase.auth.getClaims()`. **Not currently used by any handler** — the one
  server function that exists (`checkVendorCompaniesHouseFn`) has no auth check at
  all and isn't called from any route, so today it's dead code without an access
  boundary if it were ever exposed.

## 5. Organisation / user model

- There is **no organisation/tenant table**. `profiles.organization_name` is a
  free-text string captured at signup, not a foreign key to a real organisation
  entity, and it is not enforced unique or reused across users signing up for "the
  same" company.
- `vendors` (and everything hanging off it) is scoped to a single **user**
  (`owner_id`), not an organisation. Two colleagues who both sign up with the same
  `organization_name` see two completely separate, invisible-to-each-other vendor
  lists.
- `team_invites` records an intended invite (email + role) tied to the inviting
  user, but there is no acceptance flow, no resulting membership row, and no role
  enforcement anywhere in the app — `ROLES` in `src/components/signup/wizard.ts`
  is UI-only copy.
- No role-based access control exists beyond Supabase RLS's binary
  "owner or not."

## 6. Vendor code

- `vendors` table fields roughly track the ERD's `vendors` suggestions
  (`company_name`≈`legal_name`, `country`, `category`, `risk_level`≈`criticality`,
  `source`) but:
  - Uses `owner_id` instead of `organisation_id`.
  - Has **no `lifecycle_status` or `monitoring_status`** column.
  - Has **`companies_house_number` as a direct column on `vendors`**, which is
    exactly the pattern the ERD explicitly warns against (§6, "Do not create
    Companies House-specific fields directly on this table" / "avoid
    `companies_house_status`") — here it's the identifier rather than a status
    field, so it's less severe, but it still couples the vendor table to one
    provider instead of using a `vendor_identifiers` table.
  - `internal_owner` is a free-text string, not a reference to an internal user.
- Three ways to create a vendor, all client-side inserts straight into `vendors`
  via the browser Supabase client (no validation beyond a Zod form schema, no
  server function, no audit trail):
  1. Manual form (`/vendors/new`).
  2. "Upload" flow (`/vendors/upload` → `/vendors/review`) — despite the ERD/UI
     copy mentioning CSV import, there is **no CSV parsing**; it stages a
     browser-only draft from the filename and lets the user hand-edit every field
     before insert.
  3. `AddVendorModal` (dashboard/vendor list quick-add) — not inspected in full
     line-by-line but wraps the same manual-entry pattern.
- Vendor dashboard health/alerts/tasks widgets are **entirely static sample data**
  (`healthData`, `alertsByType`, `upcoming`, `materialChanges`, `tasks`,
  `sampleVendors` constants in `dashboard.tsx`) — not derived from
  `vendor_monitoring_alerts` or any live table.

## 7. Companies House integration (vendor code, cont'd)

This is the most ERD-aligned part of the codebase — it's a clean, well-tested,
provider-scoped module, but it is a **single-provider implementation**, not the
provider-agnostic framework the ERD calls for:

- `client.ts` — HTTP adapter, Basic-auth with API key as username, discriminated
  `CompaniesHouseResult` (never throws), maps 401/403/404/429/5xx/timeout/parse
  errors to typed `CompaniesHouseErrorType`s. Matches ERD §16, §25 closely.
- `normalize.ts` — pure function, raw profile → `NormalisedCompanySnapshot`.
- `detect-changes.ts` — pure diff of two snapshots into `DetectedChange[]` with a
  deterministic severity model (`critical` only for transition *into* a fixed set
  of risk statuses; `attention` for name/address/SIC changes; `info` for
  type/due-date changes) and a deterministic `dedupeKey` builder. This matches the
  ERD's §21 materiality approach in spirit, but severities/reasons are hardcoded
  in one function rather than a rules table, and there's no `materiality_reason` /
  `recommended_action` text stored anywhere (the alert has `severity` only).
- `monitor.ts` — pure orchestration (`runCompaniesHouseCheck`): fetch → compare
  against latest stored snapshot → insert snapshot (always, even with no changes)
  → insert deduped alerts. No previous snapshot ⇒ treated as baseline, changes
  suppressed for that first run — matches ERD §18 baseline logic. Storage is
  injected via a `MonitoringStore` interface, which is the one place in the repo
  that already looks like the "provider abstraction" the ERD asks for (§15),
  though it's only implemented for Companies House.
- `monitor.server.ts` — wires the pure orchestrator to the real Supabase
  service-role client; also exports a `createNullStore()` dry-run mode.
- `check.ts` — the only server function (`checkVendorCompaniesHouseFn`), not
  called from any route/component yet, and not gated by `requireSupabaseAuth`.
- `scripts/check-companies-house.ts` — Bun CLI for manually triggering a check
  (`bun run ch:check <companyNumber> [vendorId] [--persist]`), useful for local
  verification against the real API.
- **No scheduling**: no `pg_cron`/`pg_net` migration, no scheduled Edge Function,
  no batch/rate-limit/backoff logic (ERD §24). Checks only run when someone
  manually invokes the CLI script or (once wired up) the server function.
- **No `change_events` table separate from `alerts`**: a detected change is
  written straight into `vendor_monitoring_alerts`; there's no intermediate
  "factual change record" independent of whether it's alert-worthy, and no
  "informational changes don't need alerts" branch (ERD §12) — every detected
  change becomes an alert row, including `info`-severity ones.
- **No Trust Profile**: nothing writes accepted/current values back after
  resolution (ERD §8, §22) — `vendor_monitoring_alerts.status` can be updated by
  the owner via RLS, but no code path does it, and there's no attribute-level
  "current trusted value" table for the UI to read.

## 8. Edge Functions / backend code

- **No Supabase Edge Functions exist** (no `supabase/functions/` dir).
- Backend logic lives entirely as TanStack Start server-side code:
  - `*.server.ts` files (import service-role Supabase client; must only be
    imported from server contexts — enforced by convention/comments, not tooling).
  - `createServerFn` handlers (`*.functions.ts`-style; currently just `check.ts`).
  - `src/server.ts` / `src/start.ts` — TanStack Start server entry and global
    middleware registration (registers `attachSupabaseAuth` as client middleware).
- This architecture can reach parity with the ERD's "Edge Functions" requirement
  functionally, but two ERD requirements assume Supabase-native scheduling
  (`pg_cron` + `pg_net` calling an Edge Function URL, ERD §24) — that pattern
  doesn't fit a TanStack Start server function without also standing up a
  publicly reachable HTTP endpoint and its own auth (e.g. a shared secret), which
  doesn't exist yet.

## 11. Conflicts with the ERD

Ordered roughly by how foundational the gap is.

1. **No multi-tenant organisation model (ERD §2, §5.1, §5.2, §27).** The single
   biggest structural gap. Everything is scoped to `owner_id` (a user), not
   `organisation_id`. Every table the ERD specifies as
   `organisation_id`-scoped (`vendors`, snapshots, alerts, audit events, etc.)
   would need a real `organisations` + `organisation_members` model and a
   migration of existing data before RLS could enforce "users cannot access
   another customer's vendors" the way ERD §27 requires. Today two different
   companies signing up are, incidentally, isolated from each other only because
   each user is a distinct owner — this happens to hold, but not for the reason
   the ERD wants (organisation boundary), and it breaks the moment two users are
   meant to share one organisation's vendors.
2. **No provider-agnostic monitoring schema (ERD §3.2, §7–§14).** The current
   tables (`vendor_company_snapshots`, `vendor_monitoring_alerts`,
   `vendor_monitoring_failures`) are Companies-House-specific in shape (dedicated
   columns per Companies House field) rather than the generic
   `external_snapshots` (JSONB `normalized_data`) / `trust_profile_attributes` /
   `change_events` / `monitoring_runs` model the ERD specifies. Adding a second
   provider (GST, sanctions, etc.) today would mean a parallel set of
   provider-specific tables rather than reusing the existing ones.
3. **No Trust Profile / current-vs-history separation (ERD §3.3, §8, §22).**
   There's no concept of an accepted "current trusted value" distinct from the
   latest snapshot. Alerts don't drive a resolution workflow that updates a
   trust attribute — `vendor_monitoring_alerts.status` exists but nothing reads
   or writes it outside RLS permissions.
4. **No `change_events` table distinct from `alerts` (ERD §11 vs. current
   design).** Every detected change becomes an alert row directly, including
   `info`-severity ones, contradicting ERD §12's "informational changes do not
   necessarily need alerts."
5. **No audit log (ERD §13).** No `audit_events` table or equivalent; nothing
   records "vendor_created," "alert_resolved," etc. as durable, app-log-independent
   records.
6. **No scheduled/batch monitoring (ERD §24).** No `pg_cron`/`pg_net`, no
   `vendor_monitoring_config`, no rate-limit/backoff/retry logic. All monitoring is
   manual (CLI script or the not-yet-wired-up server function).
7. **Companies House identifier lives on `vendors` directly (ERD §6, §7).**
   `vendors.companies_house_number` instead of a `vendor_identifiers` table —
   exactly the anti-pattern the ERD calls out, applied to the identifier rather
   than a status field.
8. **Auth boundary gap on the one server function that exists.**
   `checkVendorCompaniesHouseFn` doesn't use the `requireSupabaseAuth` middleware
   and isn't scoped by organisation/owner — currently harmless because nothing
   calls it, but it would need both an auth check and an
   owner/organisation-ownership check on `vendorId` before being exposed to the UI,
   per ERD §27.
9. **Dashboard is not wired to real monitoring data (ERD §4 Frontend
   responsibilities, §23 Vendor Health).** All health/alert/task widgets are
   hardcoded sample arrays; there is no alerts screen, alert investigation view,
   or monitoring-settings UI at all yet, despite being explicit ERD frontend
   responsibilities.
10. **Historical secret exposure.** `.env` (including what were live Supabase and
    Companies House keys) was committed to git history before being gitignored —
    conflicts with ERD §27's "external provider API keys remain server-side" /
    §16's "keep API keys outside source code and configuration committed to the
    repository," in spirit if not in the current working tree.
11. **CSV import is not implemented (ERD §2 "CSV/imported vendors").** The
    "upload" flow only captures a filename and lets the user hand-type every
    field; no file is parsed.
